# Retro — panel-bridge MVP (2026-10-08)

Plain summary of how this repo got built, what it cost, and where the next
build should run. Written after a review pass on 2026-10-13.

## What was built

`panel-bridge` is the MVP for a bubble translator over webtoons (working name
"bubble-translator"). It detects and classifies speech bubbles on a comic panel
into four types — gradient-narration, white-on-black dialogue, black-on-white
dialogue, and loose text over art — outlines each one, and can run end-to-end on
a live Naver Webtoon page.

- `marker/` — the layer-1 bubble marker (`bubbles.ts`, `host-page.tsx`, tests).
- `m1/` — the demo pipeline: capture → detect → outline → counts table
  (`npm run demo:m1` opens Earth Game ch.1 on Naver and outlines every bubble).
- `docs/` — `SOURCES.md` (source map), `adapter-contract.md`, and the two M1
  results/trials write-ups.
- Root: TypeScript, Playwright-based capture, MIT licence, GitHub Actions test
  job, and a README with a real detector screenshot.

Publisher episode images stay in the gitignored `work/` — they never enter git.

Build timeline in this repo's history: initial commit, vision + layer-1 marker
and adapter contract (2026-10-08), the M1 live-page detector (2026-10-10), then
v0.1.0 published with CI, MIT licence and README (2026-10-11), plus two small
install/demo fixes.

## What it cost on grok.com

Madan built the MVP in grok.com **build mode**: about **30 minutes** of wall
clock, but a **heavy credit burn** — build mode regenerates whole files and
re-runs the app repeatedly, so iteration is fast but expensive per turn.

## What a lane build would have cost

The same MVP built by a free Mac lane (this `qoder` lane, or any other):

- **Credits: ~0** — a lane runs on the local model/API budget, not grok build
  credits.
- **Wall clock: longer per feature** — a lane does one ticket per run, so the
  MVP would have taken several runs (marker, then M1, then publish) spread over
  a day or two rather than 30 focused minutes.
- **The catch:** the grok-built result still needed cleanup that a lane would
  have caught for free — the two post-v0.1.0 install/demo fixes, README rewrite,
  licence, CI. Grok produced a working demo fast; hardening it took more passes.

So the trade was **grok: fast first draft, paid, then lane-style cleanup anyway**
vs **lane: slower first draft, free, hardened as it goes**.

## Where builds should run next time

Per rule R1 (a free Mac lane does any job it can; only route to paid when it
needs connectors/browser/judgment the lane lacks):

- **Default to a lane for MVP scaffolding, tests, and any code we then maintain.**
  It costs no build credits and the review/CI/licence hygiene lands in the same
  pass instead of a paid prototype plus a free cleanup PR.
- **grok.com build mode earns its credits only when the leverage is real**: a
  throwaway high-fidelity prototype to validate an idea in minutes, or a job that
  genuinely needs grok-only judgment. Treat the credit spend as budget, not free
  iteration.
- For panel-bridge specifically: the detector and demo are now maintained code
  with tests and CI, so further work should run in a lane, not build mode.
